A fraud model can have an excellent ROC-AUC and still be a poor production system.

Fraud modelling is constrained by much more than predictive performance. Data availability, leakage, temporal drift, review capacity, latency, feature stability and business cost all influence whether a model is actually useful.

The central idea

Let the agent reason about the problem. Let deterministic code enforce the rules.

03

Point-in-time correctness

Suppose a transaction occurs at T0. Every feature used by the model must represent information that genuinely existed at that moment.

T0 · SCORING

Information available at decision time

Transaction amount, device information, account age and historical behaviour may be valid inputs.

T+7 · INVESTIGATION

New information begins to appear

Investigation processes can generate information that did not exist at T0.

T+14 · CONFIRMED FRAUD

Predictive — but unavailable at T0

Confirmed-fraud information may be highly predictive, but using it at T0 creates temporal leakage.

Rule:

Predictive power does not make a feature valid. Availability at the scoring timestamp does.

04

Feature selection is a sequence of gates

With hundreds or thousands of candidate features, simply ranking everything by feature importance is not enough.

The pipeline maintains a feature registry containing candidate features and their metadata. The LLM agent uses the declared fraud use case to select and prioritise relevant features from this registry — for example, seller-level behaviour for seller fraud. The deterministic gates then verify availability, point-in-time correctness, leakage, stability, redundancy and predictive contribution.

An LLM agent first interprets the fraud use case and prioritises relevant feature families. For example, seller fraud may require seller-level behaviour, while account-takeover detection may emphasise device and login behaviour. Deterministic gates then verify that the selected candidates are safe, available and useful.

FEATURE REGISTRY Use case → relevant feature candidates

The registry acts as the source of truth for available features and their metadata. The LLM agent selects or prioritises candidates for the requested fraud use case; deterministic gates validate them before model search.

Use-case fit

An LLM agent interprets the fraud use case and selects or prioritises candidate features that are relevant to that decision before deterministic quality gates are applied.

EXAMPLE

For a seller-fraud use case, the agent may prioritise seller-level behaviour such as seller_txn_velocity_24h, seller_chargeback_rate_30d, and seller_account_age, while deprioritising buyer-only features that do not describe seller risk.

07

Why TPE?

When every model evaluation is expensive, the goal isn't to try everything. It's to spend the experimentation budget where it is most useful.

Imagine a search space containing 1,000 possible configurations. Each configuration can combine a model family, feature subset and hyperparameters. Training every possibility may be unnecessary.

RANDOM SEARCH

Sample independently

Configurations are sampled according to the search strategy without using the performance history to concentrate future trials.

TPE

Learn from trial history

TPE uses previous observations to estimate which parameter regions are more promising, then favours useful areas while still exploring.

Why it matters for fraud modelling

Fraud model search can span multiple dimensions simultaneously: model family + feature subset + hyperparameters. If each evaluation is expensive, learning from previous trials can reduce wasted computation.

Experimental results

Architecture explains how the system works. Experiments demonstrate whether each modelling decision changes the way the problem is evaluated.

Rather than presenting numerical results without the underlying dataset, split definitions, trial logs and reproducibility artifacts, this section focuses on the experimental progression: what is changed in each experiment and what question that experiment is designed to answer.

Experiment Validation Objective What it tests
Default AutoML Random ROC-AUC Establishes how a conventional AutoML setup performs when using a random train/validation split.
Temporal baseline Temporal ROC-AUC Tests whether performance changes when validation reflects the chronological nature of fraud data.
Business objective Temporal Catch@1% Changes the optimisation target from general ranking quality to the operational fraud-review constraint.
CASH + TPE Temporal Catch@1% Tests whether joint model-family and hyperparameter search can use previous trial outcomes to make the search more efficient.
Full pipeline Temporal Catch@1% Evaluates the complete workflow, combining point-in-time-safe data, feature gates, business-aligned evaluation and guided model search.

Why structure the experiments this way?

Each experiment isolates a modelling decision. The first comparison highlights the difference between random and temporal validation. The next changes the objective to match the fraud team's review capacity. CASH + TPE then tests the search strategy, and the final experiment evaluates the complete pipeline as an integrated workflow.

This progression makes the contribution easier to reason about without claiming numerical improvement that cannot be independently reproduced from the information published on this page.

11

The bigger lesson

The interesting part of an agentic fraud modelling system isn't simply adding an LLM to an AutoML pipeline.

It is connecting business intent, temporal correctness, feature eligibility, model search and operational evaluation into one reproducible workflow.

LLMsReason
Deterministic pipelinesEnforce
OptimisersSearch
Temporal validationChallenge
Business metricsDefine success

The model is still important. But the larger engineering challenge is building a system that can reliably decide what model should be built, what information it is allowed to see, how it should be evaluated, and whether its performance actually matters to the business.
